## Первый запуск

1. Откройте **этот worktree** в Unity **6000.6.8f1**, дождитесь импорта и проверьте Console. Зависимости: NGO **2.13.3**, Unity Transport **6.6.0** из `packages-lock.json` (минимальная зависимость NGO — 2.6.0). Не копируйте Library другого проекта.
2. Выполните **Tools → Mad Machines → Network → Create or open sandbox**. Новая сцена и prefab генерируются с `NetworkPhysicsState`. Если ресурсы уже создавались NETWORK 01, выполните **Upgrade sandbox replication**: команда заменяет только `NetworkTransform` / `NetworkRigidbody` в двух prefab, сохраняя пути, GUID, остальные компоненты и ссылки. Она сохраняет prefab сразу; при необходимости откатите их через Git. Сцена не перегенерируется. Повторный вызов пропускает обновлённые prefab.
3. Выполните **Validate sandbox assets**, затем **Checks → Run command policy checks**. Вторая команда проверяет команды, перезарядку, буфер интерполяции и аргументы запуска без Play Mode; она не проверяет транспорт или физику. Результатов её выполнения пока нет.
4. Выполните **Build Windows client**, затем **Build Windows dedicated server**. Нужны соответствующие модули Windows Build Support и Windows Dedicated Server Build Support. Команды проверяют ссылки и явно собирают только `Networking/Scenes/NetworkSandbox.unity`; общий список сцен не меняется.
5. Из PowerShell в worktree запустите:

   ```powershell
   $run = & ./Tools/Network/Start-LocalSandbox.ps1
   ```

   Скрипт ждёт готовности сервера, затем открывает два клиентских окна. Сервер скрыт, привязан к `127.0.0.1`. Журналы и файл остановки находятся в новой папке `Logs/Network/<запуск>`. Другой порт: `-Port 7780`. Скрипт не собирает проект и не удаляет прежние журналы.
6. Выполните сценарии A–F ниже. Штатная остановка сервера:

   ```powershell
   New-Item -ItemType File -Path $run.StopFile -Force | Out-Null
   $run.Server.WaitForExit()
   ```

Собирайте обе роли **из одних сгенерированных ресурсов и .meta**. Сохраните `Networking/Generated`, `Networking/Scenes` и метаданные вместе. Протокол повышен до **2**: NETWORK 01 и NETWORK 02 намеренно не соединяются, поскольку изменён набор NetworkBehaviour. Сохраняются игровой сценарий, управление, параметры запуска и пути сборок. Старые бинарники нужно пересобрать.

## Находки и изменения

| Находка при чтении кода | Исправление |
| --- | --- |
| Server Authority у `NetworkTransform` не запрещает владельцу вызвать SetState: встроенный RPC принимает координаты, поворот и масштаб. Проверка собственного RPC управления этот путь не закрывает. | В двух prefab используется `NetworkPhysicsState`: позу пишет только сервер в NetworkVariable; принимающих координаты RPC нет. |
| В NGO 2.13.3 есть также приватный SetStateClientRpc с разрешением по умолчанию Everyone, без проверки источника внутри метода. OnClientRequestChange относится только к другому RPC. | Полигон больше не включает этот компонент и его RPC. Это статический вывод о поверхности доверия, а не воспроизведённая атака. Пакет и его внутренние таблицы не модифицируются. |
| Fire=true мог быть затёрт Fire=false до FixedUpdate, теряя уже принятую просьбу выстрелить. | Буфер сохраняет запрос до ближайшего физического шага, не дольше 250 мс. Очереди будущих выстрелов нет. Удержание огня ограничено серверной перезарядкой. |
| RPC не учитывал выключенный адаптер, завершение сессии и соответствие текущему PlayerObject. Состояние при disable/повторном spawn не сбрасывалось. | Проверяются активность, владелец и назначенная машина; ввод сбрасывается при despawn/disable/spawn. |
| NetworkManager переносил Network session в DontDestroyOnLoad; при смене сцены оставалась сессия со ссылками на удалённые точки появления. | Manager возвращается в сцену сессии. При выходе восстанавливаются изменённые глобальные параметры; повторный manager блокируется. |
| Исключение при spawn машины оставляло подключение без машины и без гарантированной очистки места. | Частичный объект удаляется, место освобождается, клиент отключается с причиной, ошибка логируется. |
| После ошибки регистрации prefab UI мог разрешить повторный запуск неполной конфигурации. | Готовность устанавливается после настройки; запуск блокируется при некорректных ссылках, Connect обрабатывает исключения. |
| SphereCast от башни не обнаруживает препятствие, перекрывающее начальную сферу. | Добавлена проверка перекрытия у башни перед проверкой канала ствола. |
| Нельзя было отличить потерю ввода от неверных чисел, старого номера или лимита частоты. Существующие неполные ресурсы молча принимались генератором. | Добавлены счётчики отказов, журнал жизни снарядов, проверка ресурсов до сборки/запуска и явная миграция. |

## Ответственность и сетевой цикл

- `NetworkSandboxSession` настраивает UTP, протокол, prefab и callbacks **до** StartServer/StartClient. Dedicated Server не создаёт локального игрока, камеры, AudioListener и HUD. Используются `StandaloneBuildSubtarget.Server` и `UNITY_SERVER`.
- Два места резервируются на approval. Сервер вручную вызывает SpawnAsPlayerObject. NGO удаляет объекты владельца при disconnect; обработчик проверяет IsSpawned перед резервной очисткой и освобождает место. Ошибка spawn также освобождает место. Снаряды принадлежат серверу и переживают отключение стрелявшего до попадания/истечения жизни.
- RPC передаёт номер, газ, руление, ручник, направление и огонь. Координаты, скорости и клиентские сообщения о попаданиях не входят в контракт. Разрешение RPC — Owner; дополнительно проверяются sender, активность и PlayerObject. Все состояния и счётчики имеют серверные права записи. Включена проверка длины NetworkVariable.
- `NetworkCommandGate` отсеивает NaN/Infinity, диапазоны, неединичное направление и повтор/старый номер через модульное сравнение uint. Лимит — 40 команд/с, запас 8. Неверная команда расходует токен, но не обновляет управление или время принятого ввода. Это ограничение прикладного обработчика, не защита транспорта от DoS.
- Клиент отправляет до 30 команд/с. В FixedUpdate адаптер с execution order −100 передаёт **последнее допустимое** движение в неизменённый VehiclePhysics, затем тот прикладывает силы; PhysX работает на 50 Гц. Между командами управление удерживается. Через 250 мс без принятой команды газ/огонь выключаются, включается ручник. Инерция, уклон и гравитация остаются. Короткий огонь сохраняется между RPC и физическим шагом; при перезарядке запрос расходуется, а не откладывается.
- Перезарядка 1,15 с и жизнь снаряда 6 с измеряются серверными монотонными часами. Скорость снаряда — 38 м/с плюс скорость машины; PhysX, CCD и проверка пути сферой определяют попадание. Сервер применяет импульс 3200 Н·с и один раз увеличивает счётчик цели; finished исключает повторное попадание. Отдача — 1600 Н·с.
- `NetworkPhysicsState` делает тела кинематическими в Awake, включает динамику **только серверу** на spawn и выключает её на despawn. Клиентский VehiclePhysics выключен; коллайдер снаряда активен только на сервере. Rigidbody interpolation отключена: сервер читает физическую позу, клиент имеет один слой интерполяции.
- На сетевом Tick 30 Гц сервер снимает Rigidbody.position/rotation и серверное время. NetworkVariable доставляет позу надёжно и по порядку, включая полное состояние позднему клиенту. Обработчик отправки NetworkVariable в NGO подписывается раньше нашего Tick, поэтому обычная передача подготовленной позы происходит на следующем тике: до одного тика дополнительной задержки. При нескольких тиках за кадр физика повторно не симулируется.
- Клиентский буфер ограничен 32 снимками. Рисуется положение на `ServerTime − 100 мс` с Lerp/Slerp; старые и повторные времена отбрасываются. При нехватке снимков удерживается последняя поза, без экстраполяции. При spawn исходная поза применяется сразу. Своя машина тоже интерполируется. Наведение/колёса сглаживаются отдельно, скорость HUD обновляется до 10 Гц.

У `NetworkCommandGate`, `NetworkCommandBuffer`, `NetworkShotCooldown`, `NetworkPoseBuffer` нет MonoBehaviour, чтения реального времени и запуска сети. Их используют адаптеры и подготовленные проверки.

## Диагностика и ручные сценарии A–F

**Все сценарии ожидают выполнения пользователем.** Записывайте commit, версию Unity, журналы и видео двух экранов рядом с результатом. Строка готовности процесса ещё не подтверждает весь сценарий.

| Сценарий | Действия и ожидаемый результат |
| --- | --- |
| A — два клиента | Сервер и два клиента: разные client ID, разные NetworkObjectId, места 1/2, машин 2/2; своего игрока у сервера нет. Третий клиент получает отказ. Проверить занятый порт, несуществующий сервер, неверный порт и существующий stop-file. |
| B — управление | WASD, задний ход, ручник, мышь и огонь работают только у владельца. Второй экран показывает ту же машину. Esc/Alt+Tab прекращают газ/огонь без паузы сервера. Столкнуть машины, пройти препятствие и трамплин: положения согласуются с задержкой. |
| C — снимки | Подключить второго клиента во время движения/стрельбы первого: исходные позы, цвет места и счётчики корректны, нет пролёта из нуля. Проверить низкий FPS, задержку/потери. При остановке состояний клиент удерживает последнюю позу. Оценить рывки после восстановления доставки. |
| D — снаряды | Удерживать ЛКМ: не чаще выстрела за 1,15 с; проверить короткое нажатие. Попадание в машину, тонкую стену, промах, перекрытые начало/конец ствола, исчезновение через 6 с. Один счётчик попадания на снаряд; после прекращения огня снарядов не остаётся сверх их жизни. Отключить стрелявшего до попадания. |
| E — жизненный цикл | Несколько disconnect/reconnect: старая машина исчезает, место освобождается, новая единственна, ввод не наследуется. Оборвать связь с зажатым газом: через 250 мс нет газа/огня, после тайм-аута транспорта машина удаляется. Остановить stop-file, перезапустить и переподключить. В Editor сменить сетевую сцену: manager/камера не остаются; повторно открыть сцену. |
| F — неверные команды | В Editor-клиенте выполнить Checks → Send invalid commands from client. Отправляются NaN, Infinity, неверное направление/руление, повтор/старый номер и пачка сверх лимита. Счётчики отказов сервера растут; через 0,6 с возвращается обычный ввод. Машина остаётся конечной, выстрелов нет. Потери UDP могут скрыть отдельные причины; точная политика проверяется отдельно без сети. |

Editor-клиент заменяет **один** из двух собранных клиентов. Откройте сцену, выберите обычный Player subtarget, оставьте `Server In Editor` выключенным и нажмите Play. Для Editor-сервера включите этот флаг и подключите два собранных клиента. Ресурсы и протокол должны совпадать. Адрес/порт доступны в HUD. Старый PlaygroundEditor.BuildAndVerify к сети не относится.

В **Network → Checks** также подготовлены:

- **Inspect running session** — текущая уникальность владельцев/мест, PlayerObject, кинематические тела клиентов, выключенная клиентская физика, серверное владение снарядами и отсутствие камеры/HUD на сервере. Запускайте после подключения, отключения и исчезновения снарядов; снимок не проверяет переходы во времени.
- **Request client teleport** — попытка записать серверную NetworkVariable и локально изменить положение/масштаб в Editor-клиенте. Ожидаема **ошибка прав записи NGO**; отключите Error Pause для этой проверки. На следующем кадре локальная подмена исчезает, сервер и второй клиент остаются на прежней траектории. Это проба штатного API, не поддельных транспортных пакетов.

Раз в 5 с сервер пишет суммарные счётчики машины: принято, лимит, значения, порядок, владелец, неактивна, тайм-ауты. Чужой RPC может быть отклонён NGO до нашего обработчика: смотрите и журнал NGO. При despawn пишется итог. Снаряды логируют создание, попадание или истечение жизни. Чужой владелец и выключенный объект отдельно проверяются в чистой политике.

## Сборка, адреса и Linux

Результаты: `Builds/Network/Client/MadMachinesClient.exe`, `Builds/Network/WindowsServer/MadMachinesServer.exe`, `Builds/Network/LinuxServer/MadMachinesServer.x86_64`. Отсутствующий модуль платформы/Server subtarget приводит к ошибке сборки; обычный Player за сервер не выдаётся.

Пример сборки одной роли пользователем при закрытом Editor этого worktree, с ожиданием завершения:

```powershell
$projectRoot = (Get-Location).Path
$unityExe = 'C:/Program Files/Unity/Hub/Editor/6000.6.8f1/Editor/Unity.exe'
New-Item -ItemType Directory -Path Logs -Force | Out-Null
$buildProcess = Start-Process -FilePath $unityExe -WindowStyle Hidden -PassThru -Wait -ArgumentList @(
    '-batchmode', '-nographics', '-quit', '-projectPath', ('"' + $projectRoot + '"'),
    '-buildTarget', 'Win64', '-standaloneBuildSubtarget', 'Player',
    '-executeMethod', 'MadMachines.Networking.Editor.NetworkSandboxEditor.BuildWindowsClient',
    '-logFile', ('"' + "$projectRoot/Logs/network-build-client.log" + '"')
)
if ($buildProcess.ExitCode -ne 0) { throw 'Проверьте журнал: сборка не завершена успешно.' }
```

Для Windows Server замените Player на Server, метод на BuildWindowsServer и имя журнала. Для ресурсов NETWORK 01 сначала выполните миграцию через Editor. Не запускайте две сборки одного worktree одновременно.

| Параметр | По умолчанию | Значение |
| --- | --- | --- |
| `-mm-address` | `127.0.0.1` | Числовой IPv4 сервера для клиента |
| `-mm-port` | `7777` | UDP-порт 1–65535, одинаковый у всех процессов |
| `-mm-bind` | `0.0.0.0` | Интерфейс сервера; локальный скрипт явно задаёт 127.0.0.1 |
| `-mm-stop-file` | отсутствует | Файл штатной остановки; существующий файл блокирует запуск |
| `-mm-server` | выключен | Серверная роль обычного Player; Dedicated Server выбирает её по UNITY_SERVER |

Для LAN серверу задайте `-mm-bind 0.0.0.0`, клиентам — его LAN IPv4, разрешите входящий UDP-порт серверу. Клиенты используют разные исходящие порты. DNS, IPv6, Relay и NAT traversal отсутствуют.

Для Linux установите Linux Dedicated Server Build Support, выполните **Build Linux dedicated server**, перенесите всю папку результата, дайте бинарнику право исполнения и запустите:

```sh
./MadMachinesServer.x86_64 -batchmode -nographics -mm-bind 0.0.0.0 -mm-port 7777 -logFile ./server.log
```

Нужны совместимый x86_64 Linux, доступный UDP-порт, сбор журналов и управление процессом. Stop-file работает и здесь; уберите старый сигнал перед новым запуском. Linux/VPS не проверены.

## Риски и расширение

- Надёжная доставка NetworkVariable при потерях задерживает следующие состояния до повторной доставки. Буфер 100 мс требует визуальной проверки при реальном RTT/jitter; своё управление тоже задерживается. Это ещё не готовый соревновательный сетевой слой.
- Короткий огонь повторяется клиентом 100 мс; потеря всех пакетов означает потерю выстрела. Буфер устраняет потерю **принятого** запроса между RPC и FixedUpdate. Вспышка — событие на снаряде перед despawn; порядок с удалением нужно проверить в Unity. Вспышки не сохраняются для позднего подключения. Удаление снаряда может опередить визуальный конец интерполируемой траектории.
- Точку появления может занимать другая машина. Защита появления, восстановление перевёрнутой машины, полноценный боевой урон и пулы отсутствуют. Для восстановления можно переподключиться.
- Нет аутентификации, защиты от транспортного DoS, испытаний повреждённых пакетов, prediction/reconciliation, rollback/lag compensation. Ограничитель команд не ограничивает стоимость декодирования NGO/UTP.
- GUID и ProtocolVersion не заменяют контроль совпадения сборок/ресурсов: используйте один commit и набор Generated/.meta.
- Для prediction нужно добавить в снимок последний **применённый** Sequence и скорости, хранить команды/состояния владельца, отделить предсказываемое представление от авторитетного тела и выполнять reconciliation. PhysX не является детерминированным lockstep: повтор контактов требует отдельного проектирования. Rollback попаданий потребует серверной истории поз и ограниченной проверки времени запросов. Буфер и тип снимка дают точки расширения; сами механики сейчас не реализованы.

## Основания ревизии

Повторно прочитаны изменённые исходники и зависимости NGO 2.13.3: NetworkManager, NetworkObject, NetworkConnectionManager, NetworkSpawnManager, NetworkTransform/NetworkRigidbodyBase, RPC attributes/messages, NetworkVariable delta/permissions, NetworkTickSystem/BehaviourUpdater; также установленный UnityTransport и существующий VehiclePhysics. Сверены сериализованные имена, существующие .meta/GUID, пути генерации/сборок, manifest/lock и версия Editor. Сцены и prefab агентом не генерировались; реальные YAML-ссылки проверит Validate после импорта.

Публичные основания: [NetworkTransform.SetState и OnClientRequestChange, NGO 2.13](https://docs.unity.cn/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.Components.NetworkTransform.html), [Dedicated Server subtarget](https://docs.unity3d.com/6000.0/Documentation/Manual/dedicated-server-build.html), [оптимизации Dedicated Server в Unity 6.6](https://docs.unity3d.com/6000.6/Documentation/Manual/dedicated-server-optimizations.html). Точные детали NGO 2.13.3 сверялись по локальному пакету. Подтверждение C# / NGO IL postprocessing, headless-сборок, сериализации после импорта, физики и плавности требует запуска Unity пользователем.
